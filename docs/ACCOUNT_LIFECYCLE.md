# Customer account export and deletion

Web Settings → Security and mobile Settings → Security use the same authenticated API. Administrative user deletion remains separate. Demo and impersonated mobile sessions cannot request customer deletion.

- `GET /api/account` or `/api/v1/account`: status, cancellation deadline, reference, retention text, ownership requirement and eligible workspace members.
- `GET .../account/export`: private JSON export of the customer's profile, authored content, private vault, notes, learning records, calendar and document metadata. Upload download links expire after one hour; download the actual uploads before requesting deletion. Exports exclude passwords, integration credentials and other members' private data. Save exports securely. The export request has a 60-second client timeout; very large accounts may need an asynchronous archive implementation.
- `POST .../account/deletion/code`: sends a six-digit email code, valid for 15 minutes. One request per minute, at most five failed code attempts per code. Only a digest is persisted. The mail job argument is encrypted; verification codes are filtered from HTTP logs.
- `POST .../account/deletion`: requires that code and exact `DELETE` confirmation. Transfers are transactional and take effect immediately. A successor must be active in the same workspace and have no scheduled deletion. Workspace ownership is transferred; project/team successors receive the appropriate membership. Operational successors must already belong to operational projects the customer does not own. Group successors must already be participants. Direct chats are never transferred or exposed to additional members. The last site administrator must appoint another administrator first.
- `DELETE .../account/deletion`: authenticated cancellation before completion. Cancelling does not undo ownership transfers. Authentication remains available during the seven-day waiting period.

After seven days, `AccountDeletionJob` rechecks ownership under a user lock. New ownership blocks deletion and exposes a recovery message in Settings. The hourly `AccountDeletionSweepJob`, with an explicit unprefixed `default` cron queue, recovers overdue requests after worker outages. The job is idempotent, retries transient failures and restores workspace context after running. Deploy migrations before restarting Sidekiq.

Completion removes personal content and active upload attachments, clears profile/identity/integration fields, removes web/mobile/MCP credentials, disables authentication permanently, and clears notification/subscription memberships. Authored chat messages become deleted messages. An anonymized user row remains because shared project, deployment, task and call history refer to its ID. A completion timestamp and random request reference remain in `account_deletion_requests`; these are not proof that historic infrastructure copies have been erased. Workspace billing is not cancelled by deleting an individual member; shared ownership and the existing workspace subscription remain with the successor.

## Retention and deployment

Application deletion does not erase database backups, access logs, external integration copies or noncurrent S3 object versions. Operations must configure and document their actual retention periods, including S3 version lifecycle and backup expiration. Any restoration from a historic backup must replay completed deletion requests before allowing customer access. Do not advertise immediate deletion from all infrastructure copies.

Production email delivery is required for verification, including SES production access or verified recipients when running in the SES sandbox. No live deletion, ownership transfer or customer email is performed by implementation tests. The mobile settings UI must be shipped in a new binary or a compatible OTA release; backend and web changes require the normal deployment. End-to-end delivery should be checked with a designated test account after deployment.
