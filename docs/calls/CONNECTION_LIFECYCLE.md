# Call connection lifecycle

Updated web and mobile clients request `media_confirmation_required: true` when creating a direct/group call or fetching join credentials. Receiving credentials leaves a participant ringing; the media-room connected callback posts `/api/v1/calls/:id/media_heartbeat` (web uses `/api/calls/:id/media_heartbeat`) to mark attendance. Token generation failure never changes attendance. Older clients omitting the flag retain the previous response behavior during rollout.

`CallPresenceSweepJob` runs every minute via the existing Sidekiq cron schedule. It queries LiveKit RoomService using a short-lived room-scoped server JWT, confirms only ACTIVE media participants, and expires joined attendance absent for two minutes. A stale party ends a direct call; a group call ends when no joined party remains. Network, authentication, proxy, and malformed-response failures skip cleanup rather than ending a potentially active call. Background mobile media remains present through the server check, without relying on JavaScript timers. Never-joined meetings retain the existing five-minute timeout and unanswered calls retain the ringing timeout.

Deploy the migration, Rails changes, and restart Sidekiq through the deployment workflow so it registers the new cron. Deploy web and rebuild mobile for the new confirmation behavior. Existing LIVEKIT_URL, LIVEKIT_API_KEY, and LIVEKIT_API_SECRET authenticate RoomService; no additional secrets are required. The configured host must expose `/twirp/livekit.RoomService/ListParticipants` as well as the signaling connection.

## Call history

Web Chat includes a Call history button; mobile Inbox → Chat includes the history phone icon. Both use paginated GET `/calls` (web `/api`, mobile `/api/v1`), ordered by creation time and ID. Only the current user's call-participant records in the current workspace are returned. History survives removal from the conversation, but callback and conversation navigation are disabled after access is revoked. External meetings in another workspace are omitted.

Duration is the user's connected interval, bounded by participant leave time or the call's end time. Missed, ringing, declined, canceled, and failed attempts show zero. Legacy records depend on their saved attendance timestamps. Quick callback starts a new call in the original conversation using its original audio/video type. Current membership, demo restrictions, and the existing one-live-call-per-conversation constraint are rechecked by the call creation endpoint. Live conversations and conversations with no other member disable callback in history; web also blocks callback while media is open. Lists fetch 25 records at a time, with deduplicated load-more results; mobile virtualizes the rows. Request failures show retry feedback.

## Meeting chat, hands, and reactions

Both call rooms include an independent room-only chat, raised hands, and five reactions. Messages and reactions use reliable LiveKit data packets on `nexushub.meeting.v1`; identity comes from the SDK sender, never from the packet. The shared controller validates packet shape, size, supported reactions, and duplicate IDs. It retains the latest 200 messages per connected client, with unread counts, failed-send draft retention, and disconnected controls. Chat is transient: late joiners receive new messages, and leaving clears the local log. It does not create conversation messages or grant guests conversation access.

Raised hands use the `nexushub.hand` participant attribute (true/empty), synchronized for late joiners, reconnects, and departures. Participant tokens now grant own metadata/attribute updates, without room-admin permissions. Server authorization continues to use the authenticated user and persisted participant records, never client-editable attributes or metadata.

Reactions expire after five seconds, keep at most eight visible items/timers, and throttle local reaction sends. Room listeners and timers are removed on unmount. Deploy Rails for the token grant, deploy web, and rebuild mobile; reconnect to acquire a fresh token. No new migration or API endpoint is required by these interaction features.

LiveKit references: https://docs.livekit.io/transport/data/packets/ and https://docs.livekit.io/transport/data/state/participant-attributes/

## Host controls and connection fallback

Host controls are available on web and native call rooms. The server checks the current host on each `/calls/:id/host_action`; no client receives room-admin credentials. Muting targets microphone tracks only and never remotely unmutes. Removal disconnects the target and records a per-call ban, rejecting new direct/link join credentials and connection confirmations. The presence sweep removes a banned identity if it reappears. LiveKit Cloud removal uses an explicit token-revocation timestamp. Self-hosted LiveKit does not revoke already-issued tokens: enforcement of a deliberately reused token is eventual through the sweep (up to a minute), so removed participants must not be issued new tokens. See https://docs.livekit.io/frontends/reference/tokens-grants/.

Host transfer preserves the original initiator and updates a separate host user. The new host must be a connected participant in the same workspace. Realtime role updates reach both platforms; the old host immediately loses server authorization, including ending for everyone. Mute/remove failures leave membership unchanged and show an error. Removing a participant is per-call and does not remove their conversation membership.

The connection indicator reports the local SDK quality and connection state; unknown quality is labelled Measuring. Weak connections show an audio-only recommendation. Selecting audio only turns off local camera/screen sharing and unsubscribes incoming video, without muting the microphone or blocking meeting chat. New remote video tracks and reconnects remain unsubscribed. Resuming remote video does not enable camera or screen sharing; explicitly publishing local video exits audio-only mode. This is an explicit fallback rather than an automatic camera change.

## Host approval and scheduled meetings

New quick meetings require host approval by default; existing rooms and conversation calls keep their prior behavior. A link holder requests admission and receives HTTP 202 without a media token. Both clients show a cancelable waiting state and poll the meeting status. Current hosts see waiting counts in Host controls and can approve or deny each request. Approval admits the identity for that call; denial is a per-call ban. Direct joins and connection confirmation also enforce admission, and canceling a waiting request does not end the room. Guests do not gain conversation/workspace access. Once a guest is approved, their admission remains valid across reconnects and host transfers for that call unless they are removed. Native media permissions are requested only after approval.

Web Chat and Mobile Inbox → Chat include Scheduled meetings. Organizers choose title, description, local start/end time, call type, and up to 100 active workspace invitees. They can edit an unstarted meeting with optimistic locking, cancel, and see RSVP statuses. Invitees can accept or decline; other users/workspaces cannot see the schedule. Invitations and cancellation/reschedule updates use the existing notification/push pipeline. Each invitation has a personal, read-only calendar entry. Meeting edits belong in Scheduled meetings, not the generic calendar editor.

In-app reminders (and configured mobile push) arrive 15 minutes before and at start. Rescheduling replaces reminder records so stale queued jobs cannot send the old schedule; description-only edits and RSVP acceptance preserve sent reminders, and elapsed reminder times are not replayed for late schedule changes; decline/cancellation disables reminders. Failed reminder delivery is retryable and record locking prevents duplicate notifications. The minute cron recovers due reminders across workspaces and completes expired/ended meetings. Scheduled cancellation/expiry closes the LiveKit room through an idempotent background job. Organizers pending account deletion or no longer active have their schedules canceled. Personal exports include owned schedules and RSVP records.

Joining opens 15 minutes before start. The organizer starts one room, then invitees follow the room link and request host approval. An abandoned, never-joined room can be restarted without recreating invitations. The organizer retains schedule cancellation rights after host transfer; in-call controls stay with the current host. Data is stored in UTC and displayed/edited in the device/browser's local timezone.
